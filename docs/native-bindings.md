# 네이티브 상속과 trait 확장 방향

렌더링 엔진의 기존 C++ 타입 관계는 보존하고, 스크립트 기능 확장은 trait과 합성으로 제공합니다. 이 문서는 구현한 바인딩 API와 후속 언어 기능의 경계를 정합니다.

## 현재 구현: 명시적인 네이티브 부모 관계

```cpp
lua.reg_class<Node>("Node")
    .reg_var("x", &Node::x)
    .reg_func("move", &Node::move);

lua.reg_class<Sprite>("Sprite")
    .reg_base<Node>()
    .reg_con<>()
    .reg_var("texture", &Sprite::texture);
```

`reg_base<Base>()`는 C++의 public하고 모호하지 않은 부모 관계를 등록합니다. `Sprite` userdata를 `Node*`, `Node&`, `const Node&`, `shared_ptr<Node>` 또는 `shared_ptr<const Node>` 인자로 전달할 수 있습니다. 부모 메서드·필드·프로퍼티도 인스턴스에서 접근할 수 있습니다. 여러 단계의 부모 관계도 등록한 경로를 따라 변환합니다.

부모 포인터는 C++ `static_cast`로 계산합니다. 부모 주소가 객체 시작 주소와 다른 다중 상속이나 가상 상속에서도 실제 부모 부분 객체를 가리킵니다. Lua에 노출하는 부모는 클래스당 하나입니다. C++에 부모가 여러 개여도 바인딩할 경로 하나를 명시적으로 선택합니다.

### 등록 순서와 이름 충돌

1. 부모 클래스의 생성자·메서드·프로퍼티 등록을 완료합니다.
2. 자식 클래스를 등록하고 가장 먼저 `reg_base<Base>()`를 호출합니다.
3. 자식 고유 생성자와 멤버를 등록합니다.

부모로 사용한 클래스는 등록 내용이 고정됩니다. 이후 부모 등록 핸들로 멤버나 생성자를 추가·교체하려 하면 오류입니다. 인스턴스의 쓰기 가능한 필드는 계속 수정할 수 있습니다.

상속받은 이름을 자식 등록에서 다시 사용하면 메서드·프로퍼티 종류와 관계없이 오류입니다. 부모 메서드가 C++ 가상 함수라면 이미 존재하는 C++ override가 실행됩니다. 바인딩에서 같은 이름을 다시 등록할 필요가 없습니다. 부모 생성자는 상속하지 않으며 자식 생성자를 직접 등록합니다.

실행 중 메타테이블을 교체하거나 스크립트 함수로 네이티브 메서드를 덮어쓰는 방식은 API로 제공하지 않습니다. Lua의 debug·FFI를 차단하는 보안 샌드박스는 아닙니다.

### 수명과 변환

- 부모 변환은 객체를 복제하지 않습니다. 참조·포인터는 같은 객체의 부모 부분을 가리킵니다.
- `shared_ptr` 변환은 원래 control block을 공유하며 포인터만 보정합니다. 부모에 가상 소멸자가 없어도 원래 소유자가 파생 객체를 올바르게 해제합니다.
- 빌린 raw 포인터를 `shared_ptr`로 승격하지 않습니다. 호스트는 빌린 객체를 사용하는 동안 수명을 보장해야 합니다.
- const 객체는 부모로 변환해도 const 보호를 유지합니다.
- 소유 값으로 받는 기존 `Base` 인자는 C++ 값 복사를 수행할 수 있으므로 엔진 객체에는 포인터·참조·`shared_ptr`를 사용합니다.
- 역변환, 형제 타입 변환, 등록하지 않은 부모 변환은 거절합니다.
- 호스트가 `Base*` 또는 `shared_ptr<Base>`로 반환하면 Base로 노출됩니다. 실제 C++ 동적 타입을 자동 탐색하거나 파생 메서드를 복원하지 않습니다. 가상 함수의 C++ 디스패치는 유지됩니다.
- 등록 관계와 고정 상태는 Lua VM별로 독립적입니다.

## 렌더링 연결 방식

[cpp_rendering.cpp](../examples/cpp_rendering.cpp)는 Node·Sprite의 부모 관계와 네이티브 명령 수집을 보여줍니다.

```sh
make binder-examples
```

스크립트는 Sprite의 위치·텍스처를 설정하고 Renderer에 등록합니다. Renderer는 `shared_ptr<Node>`로 수명을 유지하고, 호스트 프레임에서 네이티브 가상 함수를 호출해 명령을 모읍니다. 이 예제는 바인딩과 명령 수집 검증용이며 실제 GPU 렌더러는 아닙니다.

게임 로직과 리소스 설정은 스크립트에서, 컬링·배칭·GPU 명령 제출은 엔진에서 처리하는 것을 기본 구조로 삼습니다. 엔진별 이벤트가 필요하면 명시적인 콜백 API를 추가하고, 구독 해제·객체 해제·실행 스레드 규칙을 함께 정의합니다. 기존 Lua 객체/함수 참조 API를 사용할 수 있지만 임의의 C++ 가상 함수 override를 자동 생성하지는 않습니다.

## 후속 설계: 네이티브 타입과 분리된 trait 구현

**이 절의 기능은 아직 구현하지 않았습니다.** 현재 `.d.arky`는 함수·구조적 테이블 계약을 제공하며 네이티브 클래스 선언을 표현하지 못합니다. 네이티브 상속의 실행 검증은 C++ 바인더에서 이루어집니다. 지금 typed 코드에서 호스트 객체를 사용하려면 구조적 선언 또는 명시적인 any 경계가 필요합니다.

후속 기능은 다음 규칙으로 구현합니다.

| 영역 | 규칙 |
| --- | --- |
| 네이티브 타입 선언 | 호스트 등록과 대응하는 명명 타입·단일 부모·멤버 계약을 선언 파일에 표현 |
| 타입 정체성 | 단순 클래스 이름 대신 모듈과 선언의 정체성으로 구분 |
| 부모 변환 | 선언된 부모 방향으로만 허용; 바인더와 같은 관계 사용 |
| trait 구현 | `impl Trait for Type`으로 타입 정의와 분리 |
| 구현의 소유권 | trait 또는 타입을 정의한 모듈에서 구현; 외부 trait과 외부 타입의 임의 조합 금지 |
| 중복 구현 | 같은 타입·trait 조합의 중복은 import 순서와 관계없이 오류 |
| 네이티브 이름 충돌 | trait 구현이 기존 네이티브 멤버를 암묵적으로 덮어쓰지 않도록 검사 |
| 기본 메서드 충돌 | 여러 trait의 충돌은 명시적 구현으로 해결; 마지막 import 우선 같은 규칙 금지 |
| 상태 | trait이 네이티브 메모리 레이아웃에 필드를 추가하지 않음; 추가 상태는 별도 객체에 합성 |
| 디스패치 | 네이티브 등록 테이블을 변경하지 않고 trait 구현을 별도로 연결 |
| 검증 범위 | 선언 계약과 C++ 등록의 일치 여부를 검증할 경로를 함께 마련 |

제안 문법의 예입니다. 지금 실행 가능한 예제가 아닙니다.

```text
impl Named for engine.Sprite
   function label(): string
      return "sprite"
   end
end
```

Arky 클래스의 `is`는 계속 trait 구현을 뜻합니다. 같은 키워드에 네이티브 부모 상속까지 섞지 않습니다. 언어 변경 시 파서·타입 검사·모듈 그래프·Lua 생성·선언 파일·에디터 문법·문서를 한 단위로 검증합니다.

스크립트에서 네이티브 클래스를 상속해 C++ 가상 함수를 재정의하는 기능은 후속 범위로 둡니다. 실제 엔진의 필수 확장 지점이 확인되면 중계 객체, 소멸 순서, 스크립트 오류, 스레드 제약을 포함해 별도로 설계합니다.

## 검증

[상속 테스트](../tests/binder/inheritance.cpp)는 부모 필드·메서드·프로퍼티, 여러 단계의 상속, 비영점 포인터 보정, 가상 상속, const 보호, shared_ptr 소유권, GC·VM 종료, 잘못된 변환, 등록 순서와 이름 충돌을 검사합니다. `scripts/test_binder.py`의 일반·sanitizer·Windows 크로스 빌드에 포함합니다.

```sh
make binder-test
make binder-sanitize
make binder-windows
```

Windows 크로스 빌드는 실행 검증과 다릅니다. Windows 실행은 해당 CI 또는 기기에서 확인해야 합니다. [바인더 API](../binder/README.md), [현재 스크립트 class·trait](classes-traits.md)를 함께 참고하세요.
